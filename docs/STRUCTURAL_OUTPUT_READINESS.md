# Metadata-only structural output readiness

[validate_readiness.py](../results/structural_pose_output_foundation/validate_readiness.py) checks terminal workflow identities and opaque byte lineage before the separately approved [raw-output packager](STRUCTURAL_RAW_OUTPUT_PACKAGING.md) can run. It does not call scientific readers, compute a pose or energy endpoint, validate numerical score semantics, authorize accuracy, run native scientific methods, or create archives. Its sole OS metadata subprocess is a filtered process-inventory query. This source layer contains no actual terminal certificate, validation grant or packaging approval.

The implementation uses Python 3.11 or later and the standard library. Its only repository-code import is the checksum-pinned opaque packager `400cc0cbc4fb3700a93403ae642c1f9dc4b5c0f468892db8f55295278d71b12d`. Production requires the exact reviewed packaging proposal `961e5537b1a48223a35cad10f61720db2c0f08772326a1b6f8892d90874bc600`, its 41 source pins, and immutable metadata pins from the published method/source distribution `bed3115a6ab2685aa3c9cd790ff5080e931ee813c37c720188b4e44901570beb`. A caller cannot replace that public source map with new production pins. Tests have an explicit TEMP-only synthetic API; the CLI has no synthetic override.

## Exact workflow closure

The checker requires all identities rather than successful-job counts:

- Main: 36 frozen conditions, three seeds and two methods, for 216 slots. All 36 actual modern condition receipts are required; prepared conditions bind three unique terminal run rows and copied configuration bytes. Source failures retain their actual three-slot failure receipt. All 108 VC seed receipts must be terminal and bound to their frozen condition, input, method, seed and artifact hashes. Main progress has 144 physical receipt records, comprising 36 modern records worth three slots each and 108 VC records worth one.
- Assembly: 12 exact conditions and three seeds, for 36 additional slots. Actual receipts bind the assembly preparation index, source condition and configuration. Full-assembly comparators already in main are not counted again.
- HADDOCK: exact schema-2 progress accounts for all 108 frozen job identities. Only 39 ready jobs require physical execution or wrapper-failure receipts; 69 source/coverage failures remain progress-only. Normal native and smaller orchestration-failure schemas are distinct. Declared model, stage-IO, configuration, input and resource-sidecar hashes are checked without decoding structures or energy tables. The recovered first job retains null original return-code/CPU/external-wall fields and `native_rerun: false`. Recovery proof, adoption and original source pins remain exact.
- Union: all 216 source slots and 108 pools must be terminal. Unique retained source IDs must equal both the complete per-success returned-model rank IDs and the fixed-score manifest keys. Physical score JSON paths must equal that set too; no orphan adoption or repair occurs. Every score record must have a terminal status and the exact source tuple, method and coordinate policy. Final canonical progress must bind the current source index and score manifest. Historical pass counts cannot substitute for final sets.

JSON floating-point tokens are retained as strings with a distinct opaque token type and are never converted to floating-point numbers. Canonical checksums serialize their original number spelling. Strings containing raw native streams are hashed without parsing their numeric contents. The only raw-model syntax recognized is contiguous `MODEL` identity and `ENDMDL` boundaries, to hash complete model blocks and bind returned ranks; atom and score lines remain opaque. Typed canonical comparison distinguishes a numeric token from a quoted string with the same characters.

The full included-plus-excluded output snapshot is checked before and after validation using the approved packager API. All 240 original first-job members must match their current physical counterparts. Every consumed file, source pin, grant and producer-context pin is rechecked at the final boundary. Missing, duplicate, pending, rebound or changed evidence raises an error; no partial readiness certificate is returned. These checks preserve failure evidence and unknown telemetry rather than inventing successes, files or measurements.

## Actual-host stopped-writer provenance

Completeness does not prove that a process has exited. Root must first prepare and review a separate schema-2 producer-context file outside the three output roots. It names scope `actual_current_host_producers_only`, canonical repository root, current hostname, `source_review_and_observed_completion_account_for_writer_lifetimes: true`, and exactly four roles: `main`, `assembly`, `haddock`, `union`. This accounts for source-defined writer lifetimes through observed synchronous completion; it does not assert an exhaustive historical PID inventory.

Each role binds its published driver source and launch provenance. `actual_known_pids` contains only recorded actual OS PIDs, or is explicitly null/empty when none were captured. When the historical inventory is incomplete, `historical_pid_inventory_complete` is false, `missing_historical_pids` remains null and `pid_inventory_reason` is `not_recorded_during_execution`. A complete recorded inventory instead requires a nonempty PID list, an empty missing list and reason `complete_recorded_inventory`. Missing IDs, start times, stop times and descendant identities must never be invented. Main and assembly must include their actual progress-driver PID because that identity is available.

Two separate checksum-pinned records are required per role. `operator_completion` records an actual observed synchronous tool wait, its transport session label as a string, and integer exit code zero. It explicitly scopes that exit to the root-managed tool session and sets `original_native_process_return_code_inferred: false`. Root may record this observation after collection; it must not claim an unavailable contemporaneous PID capture. In particular, a successful HADDOCK recovery-driver session does not establish the original first native process's return code, CPU or external wall time; those fields remain null under the unchanged recovery checks.

`source_wait_proof` binds the exact published driver/helper source-pin set, the role's fixed wait-contract label, `all_workers_and_child_writers_joined: true` and `no_unjoined_writer_lifetimes: true`. Main and assembly wait for native methods through `subprocess.run`; main also waits for VC and its fixed helper. HADDOCK collects active future results and joins the executor before returning. Union scoring waits for each fixed helper sequentially before final progress. Every role also pins the synchronous provenance writer. Root's source review and actual completed tool-wait proof must cover any outer wrapper, logging or metadata writer lifetime. A new or unjoined writer mechanism requires a new review, never an optimistic completion flag. POSIX session separation is compatible with this proof when the child is still synchronously waited for.

Known actual-host PIDs are queried for existence before and after validation. A present, inaccessible or reused PID fails closed. A separate `/bin/ps -ww -axo pid=,command=` query requires no current benchmark-writer candidates. It matches literal driver/module/result-path markers and conservatively flags recognized native writer programs, including relative commands. It does not broadly match every process containing the repository root or exclude arbitrary ancestors. Only sanitized candidate PID, tags and command hash can leave the matcher; unrelated command lines and environment data are discarded. Unresolved candidates fail closed, including conservative false positives. Scoped launch/exit evidence must likewise avoid unrelated OS commands or private environment values.

The command scan cannot identify a historical anonymous `python -`/stdin wrapper by command alone and is not exhaustive historical PID discovery. Source-bound synchronous tool completion covers that limit; missing historical IDs stay explicit. Known-PID checks, this supplementary current-command scan, absent coordinator lock, complete workflow identities and stable full snapshots are all required together. No stopping or terminating signals are sent and no lock is deleted. Portable archive replay must never query the historical PIDs in this actual-host record.

Schema 2 replaces the pre-production `e469a4c5a6b8b830ab82cd7fe9f8e886e201aea8c7f894e65bf0dcc6548f6ef9` context contract, which incorrectly required nonempty exhaustive PID lists despite unrecorded fixed-score process history. No actual readiness certificate was produced with that earlier source. The correction changes operational evidence requirements; every workflow, identity, source, MODEL, historical-240 and snapshot gate remains intact.

## Separate root grants

A future validation grant outside the output roots must have schema 1, status `approved_metadata_only_terminal_validation`, `validation_authorized: true`, the exact plan path/bytes/SHA pin, reviewed validator and packager SHA256 values, and the producer-context pin. This grant authorizes only the read-only validation and explicit new readiness output. It does not authorize archive creation or accuracy. No such grant is supplied by this source proposal.

After root source review and an explicit grant, the future command is:

```sh
python3.11 results/structural_pose_output_foundation/validate_readiness.py \
  --root REPOSITORY --plan PLAN --authorization VALIDATION_GRANT --output NEW_READINESS_JSON
```

`validate(...)` itself returns a record and writes nothing. The CLI requires a fresh explicit output outside the three source trees. A successful record has status `all_structural_sources_terminal_metadata_only`, exact counts, final identity-set digests, snapshot SHA, every consumed file pin, historical overlap proof, and actual-host PID-check provenance. It explicitly reports that no geometry, energy or accuracy endpoint was interpreted or computed. Root must review that concrete record before issuing the different `approved_terminal_structural_raw_packaging` approval consumed by the packager. The independent global accuracy gate remains separate.

Run synthetic controls with `python3.11 -m pytest -q tests/test_structural_output_readiness.py`. They use private temporary roots, fake workflow files, patched PID checks and mocked process-inventory output, never actual workflows or actual current/historical process scans.
